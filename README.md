# 三文鱼大模型 · salmon-desktop-control

一个给 AI agent 用的 **Windows 桌面操控技能**：像素级看见屏幕、像素级定位目标、把动作投给指定窗口，
并且**让闭环跑在本地进程里，而不是每一步都问一次模型**。

适用于自绘 UI、游戏画面、被遮挡的窗口、取色、模板找图、OCR 读字这类"没有语义树可依赖"的场景；
也适用于需要 30 次/秒以上反应速度的实时操作（音游、接球、连点）。

## 30 秒上手

```bash
git clone https://github.com/<你的账号>/salmon-desktop-control.git
cd salmon-desktop-control
pip install -r requirements.txt

python scripts/svc.py start                 # 起常驻服务（首次会加载 OCR，约 10s）
python scripts/mc.py ping                   # {"ok":true,"pong":true,...}  0.9ms
python scripts/mc.py shot --region 0,0,800,600 --out shot.png
python scripts/mc.py find-color --rgb 255,45,45 --tolerance 40 --hwnd <窗口句柄>
```

把它接到 agent 客户端：把整个 `salmon-desktop-control/` 目录放进你客户端的技能目录
（例如 `~/.<你的客户端>/skills/`），`SKILL.md` 就是技能说明书，没有额外依赖文档。

## 四路实测对比

同机同屏（1920×1200）、同一个自绘 tkinter 靶子窗口（782×648 物理像素）、遮挡物压在靶子上，
**模型不在环**，每格取 5 次中位数，2026-10-03 实测。判"抗遮挡"的方式很硬：
统计抓回来的图里是靶子自己的深色底、还是遮挡物的灰底（各占百分比）。

| | 抓一张窗口图 | 读语义/文字 | 被完全遮挡时 | 后台输入（不抢前台） | 装上去多大 |
|---|---|---|---|---|---|
| **三文鱼**（本仓库） | 屏抓 15.3ms · PrintWindow 17.9ms · **WGC 9.9ms** | 区域 OCR 167ms · 颜色/模板找图 <20ms | ✅ pw 96.1% / wgc 91.0% 仍是靶子自己 | ✅ `--via post` PostMessage 直投句柄 | Python 依赖 211 MB |
| **windows-mcp 4.0.10**（GitHub 上的热门桌面 MCP） | 整屏截图 416ms | UIA 元素树 5.4s | ❌ 截图里 91.7% 是遮挡物 | ❌ 走全局 SendInput，前台丢了就打进别的窗口 | 独立环境 158 MB |
| **客户端自带 computer-use 0.1.0**（Rust/UIA/WGC） | 按窗口取状态 291ms（树+图一次给） | UIA 树（长列表要限 `max_tree_nodes`） | ✅ 90.3% 是靶子（底层就是 WGC） | ✅ UIA Invoke 不动鼠标 | 2.5 MB（随客户端） |
| **Windows 原生**（PowerShell + .NET，零安装） | `CopyFromScreen` 14.1ms | 无 | ❌ 屏抓 0.1%；`PrintWindow` P/Invoke 自己写才有 91.2% | ❌ `SendKeys` 只看前台 | 0 |

读这张表的正确姿势，也是这个项目真正的立场：

- **单点抓图速度并不构成优势**。Windows 原生自己写 `PrintWindow` 也是 12ms 量级。三文鱼的价值在
  它把"捕获形态选择、坐标对齐、DPI、找图找色找字、输入投递、循环回路、失败诊断"做成了一个能直接调的常驻服务。
- **按窗口取语义树，客户端自带的 computer-use 是最好的现成方案**，本仓库默认建议：
  有语义就用语义，本技能负责"没有语义、要像素、要速度"的那一半。
- **UIA 类方案读一次树要 5 秒级**，做"逐帧反应"的实时操控根本不够；这就是 `guard` 反射回路存在的理由。
- **屏幕抓取在遮挡下必瞎**，这不是实现瑕疵而是 OS 语义。本技能三种形态（screen / PrintWindow / WGC），
  `auto` 规则自己按 z-order 判断该用哪个，并在 WGC 会话停更时退回 PrintWindow。

## 它能做什么（43 个 op）

捕获（屏抓 / PrintWindow / WGC 三形态 + 整屏或区域）、找图（模板多尺度）、找字（OCR + 按文字定位并点击）、
找色（含实心色块判据，专门治"纯色小块假命中"）、鼠标（移/点/双/右/拖/滚/按住）、键盘（打字/快捷键/按下-松开）、
后台投递（`--via post`）、窗口（列表/置顶/恢复/挪走/藏起/批量还原）、等待（等文字出现/消失、等画面稳定、可只等窗口自身稳定）、
`batch` 把一串动作压成一次 HTTP 往返、`guard` 反射回路（模型只下发条件与动作脚本，本地逐帧判、逐帧出手）、
顶部操作横幅，以及 `front-policy` 抢前台硬开关。

## 为什么长这样（设计取舍）

- **常驻服务**：每条命令重启一次 Python 要 2–5 秒（解释器 + 加载 cv2/OCR），
  常驻之后 `ping` 0.9ms、`click` 2ms、区域 OCR 0.11–0.3s。
- **三种捕获形态并存**：`screen` 是 GPU 合成后的真实画面；`pw` 抗遮挡但在 DPI 无关窗口上只印出左上 1/4
  （技能会自动识别并告诉你乘几）；`wgc` 抗遮挡、满分辨率、坐标 1:1，实测约 10ms/帧。
- **WGC 跑在独立 worker 进程里**：第三方绑定 `windows-capture` 在新建会话时会 access violation 打死宿主进程，
  所以把它隔离出去，崩了只损失 worker，服务 10ms 自愈重建。
- **模型不在环**：实测一轮模型生成要消耗 21–58 格游戏时间，而本地反射回路是 30ms/帧。
  所以"决策在本地、策略由模型下发"是硬约束。
- **失败必须给下一步**：找不到目标时返回的不是 `count: 0`，而是"这次用了哪个形态、为什么没找到、
  该换哪条命令"。找不到原因比失败本身更费时间。
- **抢前台是策略而不是自觉**：`SALMON_ALLOW_FRONT=0` 或 `mc.py front-policy --allow 0` 之后，
  任何自动置顶一律跳过并计数 —— 多人/多 agent 共用一台桌面时这是必需品。

## 已知边界（别绕过这些）

- 只支持 Windows 真实桌面会话；远程桌面 / 锁屏 / 虚拟显示拿不到画面。
- **UIPI 提权窗口点不动**（管理员权限进程），系统边界。
- **DirectX 独占全屏**仍可能给黑帧，窗口化/无边框窗口才稳。
- **联机游戏的反作弊是红线**（EAC/BattlEye/ACE 及各类服务端检测），本技能不用于任何线上对战游戏。
- 中文输入法会吃掉部分 ASCII 键；高频连点会被目标 UI 线程合并（需 ≥50ms 间隔或 `batch` 内加 `sleep`）。
- 屏幕几何会变（改缩放、投屏、换显示器都会），**任何缓存的坐标都必须每帧重取**。
